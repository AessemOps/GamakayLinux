# 2.4 GHz wireless (LK67)

Status: reconnaissance done, one blocking hardware question open. Branch
`feat/wireless-24g`.

## Why

The LK67 is tri-mode (the firmware carries 2.4 GHz sleep timers alongside the
Bluetooth ones), but the receiver has never been supported: `Connection::Receiver`
exists and nothing ever produces it, the udev rule's receiver `idVendor/idProduct`
pair is a documented TODO, and `docs/protocol.md`'s transport matrix has `?` in
every 2.4 GHz cell.

Between the two items the user reports **2.4 GHz stopped typing after the 2026-10
firmware update**, which makes "typing" the first question and "config over 2.4 GHz"
the second.

## Findings (2026-10-17)

**The receiver is `25a7:fa17`** — "Areson Technology Corp / RONGYUAN 2.4G Wireless
Device" (`manufacturer=RONGYUAN`, `product=2.4G Wireless Device`), full speed, three
HID interfaces when it configures:

| interface | descriptor |
|---|---|
| 1.0 | Mouse (`0x0001:0x0002`): buttons, X/Y, wheel, AC Pan. No feature report. |
| 1.1 | Vendor `0xFF00:0x0E` **Report ID `0xBA` = an output *and* an input report, 31 bytes each**, plus System Control (`0x02`), Consumer (`0x03`) and a 120-bit keyboard bitmap (`0x04`). No feature report. |
| 1.2 | Boot keyboard (`0x0001:0x0006`): modifiers, 6-key array, LED output. No feature report. |

**No node declares a feature report**, so the whole `gamakay` protocol — 64-byte
HID feature reports, report id 0 — cannot be addressed over this receiver as
written; every selection path here requires a ≥64-byte feature report. The only
writable channel it offers is the 31-byte `0xBA` output report.

**Observation of the fault.** On 2026-10-17 10:41 the receiver sat at `3-4`
enumerated but **with no configuration selected**: no `3-4:1.x` interface
directories, `bConfigurationValue` empty, and `lsusb -t` printing the device with
no interface lines (the wired board at `3-1` has `1.0`/`1.1` and works). In that
state there is no HID, no hidraw and no input device, so nothing can type.
This is a USB-level fault, independent of the protocol.

**GAMAKAY's own model** (from `GAMAKAY_v4_setup_3.0.27`, `dist/index.99d3a344.js`):

- The registry knows three connections: `connect:"usb" | "bt" | "24g"`.
- Receiver ("dongle") entries are their own devices — `type:"dongle"`, listed under
  GAMAKAY's vendor id `0x3151` on **usage page `0xFFFF` usage `2`**, flagged
  `dongle_common`; Bluetooth entries are flagged `ble` on page `0xFF55`/`0xFF66`.
- A dongle is enumerated as a `dangleCommonDev` carrying a **keyboard and a mouse**
  sub-device, each with `{isOnline, battery}` — this is where our doc's
  "battery | receiver status only" row comes from — over a **protobuf** message
  (`oneofDev`/`oneofKind`), not the yc500 feature protocol.
- It sends config through `sendFeatureReport` (report 0, checksum at byte 7/8 —
  our protocol) and reads through `receiveFeatureReport`; the `sendReport` /
  `inputreport` pair exists but the observed dongle path is the protobuf one.
- `25a7:fa17` itself is **not in the registry** (other `0x25A7` PIDs are), so
  GAMAKAY's app may not configure this exact receiver either.

**The Fn layer has no wireless keys.** Read from the board: `Fn+Q/W/E/R` = macOS /
Android / iOS / Windows mode (slots 8/14/20/26), `Fn+X/C/V/B` = Profile 1..4
(16/22/28/34), the arrows = brightness/speed, the right column = light mode / side
mode / backlight. Nothing selects a radio mode and nothing pairs, so mode selection
and pairing are physical (the keyboard's switch), not configurable from an app.

## Deliverables

1. **Identity gate, both front-ends.** The CLI currently accepts any node with a
   settings report whose bus is USB: with no GamaKay board attached it selects
   **`/dev/hidraw5`, the Corsair M65 mouse**, and only the permissions stop it.
   The GUI gate added in the 0.1.0 review requires a known USB id, which would
   instead *refuse the board over Bluetooth* (HOGP surfaces under the adapter's
   ids). Both must use one rule: a known USB id, or Bluetooth — with the CLI's
   `--force` as the escape hatch.
2. **Recognise the receiver.** Record `25a7:fa17` and produce
   `Connection::Receiver` for it, so `list`/`info` name it instead of calling it
   USB. Wire the udev rule's TODO (id pair + the "RONGYUAN 2.4G Wireless Device"
   name, which the existing `*GamaKay LK67 Keyboard*` match does not cover).
3. **Decide the config question with evidence.** Probe whether the receiver's
   `0xBA` channel answers anything (feature ioctls are expected to fail — the
   descriptor declares none). If it carries no settings protocol, the honest
   outcome is "2.4 GHz is typing-only; configure over USB or Bluetooth", recorded
   in the transport matrix rather than guessed at.

## Open questions

- Does the receiver expose a settings channel once the keyboard is paired and
  online (does its descriptor change)? Needs a working RF link to tell.
- Is `25a7:fa17` a plain pass-through with no status channel at all, or does the
  `0xBA` report pair carry the vendor's status (online/battery)?
- Was the post-update typing failure the unconfigured-USB state above, or a lost
  RF pairing? A replug test separates them.

## Method

Read-only throughout, per the Phase 0 rule: descriptors from sysfs, no writes to
the board. Probes of the receiver's nodes need access the udev rule does not yet
grant (`/dev/hidraw*` for `25a7:fa17` is root-only).
